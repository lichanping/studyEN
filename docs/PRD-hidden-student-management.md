# 隐藏学生名单维护 - PRD

> 文档日期：2026-08-17  
> 状态：已完成一轮 Review，待实现

## 1. 背景

当前各页面的 `userName` 下拉会通过 `commonFunctions.filterLegacyStudents()` 过滤一份硬编码名单。

现状问题：

- 每次新增需要隐藏的学生，都要直接改代码并发版。
- “legacy 学员过滤”和“临时运营隐藏”共用同一份硬编码名单，维护语义不清。
- 维护入口不在 UI 中，后续继续加人或恢复展示都不方便。

本次新增的隐藏诉求已经证明，这类操作属于高频运营维护，不应继续依赖开发改代码。

## 2. 目标

- 提供一个可视化页面/区域，让我可以自行维护“隐藏学生名单”。
- 被隐藏的学生，在正式课、阅读课、体验课、抗遗忘页、排课相关学生选择中默认不出现在 `userName` 下拉或学生列表中。
- 下次新增/移除隐藏学生时，不需要再改代码。
- 不影响历史数据、统计、工资、排课存量记录，只影响“选择时是否展示”。

## 3. 非目标

- 不做后端存储或多人协同。
- 不改动历史课堂记录、月末总结、工资账本中的既有姓名。
- 不做模糊搜索或昵称推荐输入；维护时仍以标准学生名为主。
- 本期不做“按老师 / 按页面 / 按时段”的细粒度隐藏规则。

## 4. 方案建议

### 4.1 入口建议

本期不单开新页面，直接挂到现有 [schedule-students-manage.html](schedule-students-manage.html) 中，增加一个“隐藏学生名单维护”区域。

原因：

- 现有页面已经承担“学生相关维护”的心智入口。
- 已有登录校验、导航、表单风格，可复用。
- 避免后续出现“排课学生维护一处、隐藏名单维护另一处”的分散入口。

UI 要求：

- 保持简洁，不新增复杂弹窗或二级流程。
- 默认在同页新增一个轻量面板即可完成“添加 / 查看 / 取消隐藏”。
- 不引入额外筛选器、标签页或复杂说明文案。

结论：本期以内聚为优先，不拆独立页面。

### 4.2 数据存储

新增本地存储键：

- `hidden-students-v1`

建议数据结构：

```json
[
  {
    "name": "徐崇楷",
    "platform": "all",
    "updatedAt": "2026-08-17T10:00:00.000Z"
  }
]
```

字段说明：

- `name`: 学生姓名，必填，精确匹配。
- `platform`: 本期固定为 `all`，表示全平台隐藏。
- `updatedAt`: 自动写入，便于核对最近修改。

### 4.3 过滤规则

统一新增共享函数，例如：

- `getHiddenStudentNames()`
- `filterHiddenStudents(list)`
- 或将现有 `filterLegacyStudents()` 升级为“内置黑名单 + 可维护黑名单”的统一入口

建议口径：

`最终过滤名单 = 内置 legacy 名单 + hidden-students-v1`

说明：

- 内置 legacy 名单继续保留，避免既有历史过滤逻辑被误删。
- 运营手动维护名单追加到可配置层。
- 各页面继续只调用一个共享过滤函数，避免行为分叉。

### 4.4 姓名别名归一化

隐藏名单维护与过滤时，必须先走 [student-name-alias.js](student-name-alias.js) 的统一映射，再参与存储和比较。

当前已知必须支持：

- `硕硕 -> 俞新硕`

规则要求：

- 在管理页输入 `硕硕` 时，保存到隐藏名单中的标准姓名应为 `俞新硕`。
- 在各页面做过滤比较时，也应先做 `normalizeStudentName()` 再判断是否命中隐藏名单。
- 若用户直接输入标准名 `俞新硕`，行为应与输入 `硕硕` 完全一致。

这样可以避免同一学生因为昵称 / 标准名不一致而出现“隐藏不生效”或“重复维护两份名单”的问题。

## 5. 页面需求

### 5.1 管理页新增区域

在 [schedule-students-manage.html](schedule-students-manage.html) 中新增一个“隐藏学生名单”面板，包含：

- 输入框：学生姓名
- 添加按钮：加入隐藏名单
- 列表区域：展示当前隐藏名单
- 每行操作：取消隐藏 / 删除

### 5.2 列表展示字段

建议列：

- 学生姓名
- 最近更新时间
- 操作

### 5.3 交互规则

- 新增时自动去重：同名学生已存在则不重复新增，只更新 `updatedAt`。
- 学生姓名前后空格自动 trim。
- 保存前先执行 `normalizeStudentName()`，再写入 `hidden-students-v1`。
- 空姓名不允许保存。
- 删除后立即生效，相关页面下次打开或刷新后恢复可见。
- 新增后立即生效，相关页面下次打开或刷新后不可见。

- 已写入历史存储的数据不做回写删除。

## 7. 用户故事

### US-01 新增隐藏学生

作为运营维护者，我希望在页面里直接输入学生姓名并加入隐藏名单，这样下次不需要找开发改代码。

### US-02 恢复展示学生

作为运营维护者，我希望能把某个已隐藏学生移出名单，这样相关页面下拉能再次看到该学生。

### US-03 避免误伤历史数据

作为运营维护者，我希望隐藏只影响“是否展示”，不影响历史统计和既有记录，避免账务或复盘数据异常。

### US-04 昵称与标准名行为一致

作为运营维护者，我希望输入 `硕硕` 或 `俞新硕` 时都命中同一个学生，这样隐藏规则不会因为别名不同而失效。

## 8. 验收标准

- AC-01：在管理页新增隐藏学生后，该学生不会出现在正式课学生下拉中。
- AC-02：在管理页新增隐藏学生后，该学生不会出现在阅读课学生下拉中。
- AC-03：在管理页新增隐藏学生后，该学生不会出现在体验课学生下拉中。
- AC-04：在管理页新增隐藏学生后，该学生不会出现在抗遗忘页学生下拉中。
- AC-05：在管理页新增隐藏学生后，该学生不会出现在排课学生管理列表与排课相关学生集合中。
- AC-06：移除隐藏后，刷新页面可再次看到该学生。
- AC-07：重复添加同名学生不会产生重复脏数据。
- AC-08：输入 `硕硕` 后，应按 `俞新硕` 存储并生效；输入 `俞新硕` 时结果一致。
- AC-09：历史统计、工资、排课原始数据不因隐藏动作被删除或改写。

## 10. 风险与取舍

- 若继续复用 `LEGACY_STUDENT_NAMES` 作为唯一名单，虽然实现快，但语义会越来越混乱。
- 若本期直接重构成完整 `student-roster-v1` 主表，设计更完整，但范围明显过大，不适合当前需求。

因此建议本期采用：

- 保留内置 legacy 名单
- 新增可维护 hidden 名单
- 用共享过滤函数做统一合并

这是最小变更、可持续维护、回归风险最低的方案。

## 11. Review 结论

本轮 review 已确认：

1. 不单开页面，直接集成到 [schedule-students-manage.html](schedule-students-manage.html)，且 UI 保持简洁。
2. 隐藏规则本期固定为 `all`，即全平台隐藏。
3. 不维护“隐藏原因”，只维护标准学生姓名。
4. 隐藏名单必须接入 [student-name-alias.js](student-name-alias.js) 的统一映射，当前至少覆盖 `硕硕 -> 俞新硕`。
