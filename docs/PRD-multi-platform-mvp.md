# 多平台扩展与学生管理灵活化（MVP）PRD

文档日期：2026-07-07  
版本：v1.0（MVP）

## 1. 背景

当前系统默认围绕单一平台“李校来啦”运行，存在两个问题：

1. 品牌与话术存在硬编码，无法自然扩展到“百分缔”等新平台。
2. 学生信息来源分散，新增学生虽可通过部分本地配置生效，但没有“平台维度”的统一管理，难以在多平台下保持一致。

## 2. 需求目标

### 2.1 业务目标

1. 平台从单平台扩展为多平台（首批包含“李校来啦”“百分缔”）。
2. 教练仍为一个人，但可在不同平台下维护独立学生池。
3. MVP 阶段实现“新增百分缔学生不需要改代码”，仅通过页面配置完成。

### 2.2 产品目标

1. 页面可切换“当前平台”。
2. 学生下拉按平台过滤，避免跨平台混用。
3. 话术中的平台名称可动态替换。
4. `schedule.html` 仍作为同一教练的统一排课视图，跨平台排课在同一时间轴统筹避免冲突。
5. 会议号按平台区分（李校来啦与百分缔独立会议号）。

## 3. 当前现状（与本需求相关）

1. 排课维护主入口：schedule-students-manage.html + schedule-students-manage.js（已支持本地覆盖与保留学生名）。
2. 课程页面学生来源存在多源合并，但不带平台字段：
- classFormal.js
- classRead.js
- classTrial.js
- anti-forgetting.html
3. 目前存在品牌硬编码文本：
- classTrial.js 中“希望你喜欢李校来啦这个平台”
- commonFunctions.js 中“我是【李校来啦】...”

## 4. MVP 范围

### 4.1 In Scope

1. 增加“平台”配置与切换能力。
2. 学生维护增加“所属平台”字段。
3. 各课程页面学生下拉按平台过滤。
4. 关键话术支持平台名动态化。
5. 保持现有本地存储方案（localStorage）以降低改造成本。

### 4.2 Out of Scope

1. 不引入后端数据库。
2. 不做多教练权限与账号隔离。
3. 不处理跨设备自动同步。

## 6. 数据设计（MVP）

### 6.1 新增存储键

1. platform-config-v1
- 用于定义平台列表与默认平台。

示例：
{
  "defaultPlatform": "lixiaolaila",
  "platforms": [
    { "id": "lixiaolaila", "displayName": "李校来啦", "active": true },
    { "id": "baifendii", "displayName": "百分缔", "active": true }
  ]
}

2. current-platform-v1
- 记录当前页面选择的平台 id。

3. 会议号平台映射（建议放在 `meeting-config.js`）

示例：
{
  "lixiaolaila": "957-2306-5683",
  "baifendii": "684-1587-8369"
}

### 6.2 兼容扩展字段

1. schedule-config-override-v1.entries[].platform
2. custom-students-v1 从 string[] 升级为对象数组（或新增 custom-students-by-platform-v1）

推荐结构：
[
  { "name": "张三", "platform": "baifendii", "updatedAt": "2026-07-07T10:00:00Z" },
  { "name": "李四", "platform": "lixiaolaila", "updatedAt": "2026-07-07T10:05:00Z" }
]

兼容规则：旧 string 结构默认归属 defaultPlatform。

## 7. 核心流程（满足“不改代码新增百分缔学生”）

### 7.1 一次性上线后的日常操作

1. 进入排课学生管理页。
2. 选择平台为“百分缔”。
3. 新增学生并保存。
4. 在体验课/正式课/阅读课切换到“百分缔”后即可直接选择该学生。

### 7.2 关键前提

1. 平台及学生数据来源已统一为“配置驱动”。
2. 课程页面均支持平台过滤。

## 8. 验收标准（AC）

1. AC-01：平台可选“李校来啦”“百分缔”，并在页面刷新后保留最近选择。
2. AC-02：在“百分缔”新增学生后，无需改代码即可在体验课、正式课、阅读课下拉中看到。
3. AC-03：切回“李校来啦”时，默认不出现“百分缔”学生。
4. AC-04：旧数据不丢失，历史无 platform 字段条目可正常展示（归默认平台）。
5. AC-05：开场与结束话术中平台名随当前平台变化。
6. AC-06：`schedule.html` 在跨平台排课时可统一查看，避免同一教练时间冲突。
7. AC-07：百分缔学生的会议文案使用独立会议号 `#腾讯会议：684-1587-8369`。
8. AC-08：仅 `schedule.html` 在切换到百分缔平台时不执行工资统计，并有明确提示；`index.html` 仍可按当前平台计算工资。

## 9. 风险与应对

1. 风险：同名学生存在于不同平台。
- 应对：内部主键使用 name + platform，展示层仅显示 name。

2. 风险：旧数据结构混用。
- 应对：读取时做 schema 兼容转换，写入统一新结构。

3. 风险：部分页面忘记加平台过滤。
- 应对：抽出统一 helper（如 getCurrentPlatform、filterStudentsByPlatform）并复用。

## 10. 里程碑建议

1. M1（0.5 天）：完成数据结构与读取兼容。
2. M2（1 天）：完成 4 个主页面（排课、体验、正式、阅读）平台切换与过滤。
3. M3（0.5 天）：文案动态化 + 验收 + 回归。

## 11. 成功定义

上线后，新增“百分缔”学生不再需要改任何 JS/HTML 代码；仅通过页面维护即可完成新增与使用。

## 13.3 课时异常提醒文案与单行复制补充（2026-08-11）

### 修复背景

`schedule.html` 的“查看课时数”会在页面顶部生成“异常学生”列表，并额外复制一份整批提醒文案。当前存在两个产品问题：

1. `30分钟剩余`、`60分钟剩余` 只要小于本周排课节数就会被标记异常，但业务要求是“只要不为 0 就不算异常”。
2. 异常学生往往需要分别通知不同排课老师，整批复制文案不便直接使用，需支持按学员逐条复制。

### 行为要求

1. `30分钟剩余` 只要数值不为 `0`，即视为正常，不因“小于本周30分钟排课节数”而标记异常。
2. `30分钟剩余` 仅在为空、无法识别或 `<= 0` 时标记为 `30分钟课时不足`。
3. `60分钟剩余` 只要数值不为 `0`，即视为正常，不因“小于本周60分钟排课节数”而标记异常。
4. `60分钟剩余` 仅在为空、无法识别或 `<= 0` 时标记为 `60分钟课时不足`。
5. `陪练服务时长剩余` 继续保持“剩余小于本周需求即异常”的现有规则。
6. 单条提醒文案直接使用异常说明本身，不再重复追加“当前剩余”后缀。
7. 未异常的额度字段不应出现在单条提醒文案中。
8. 学员系统未查到的场景保持原样，仍提示核对学员名称与待核对课时。
9. 异常学生置顶列表中，每一行状态栏都要提供一个 `复制` 按钮。
10. 点击该 `复制` 按钮时，只复制当前这一名学员的单条提醒文案，不再复制整批异常学生汇总文案。
11. 正常学生列表不展示该 `复制` 按钮。

### 示例

- 若仅 `quotaAccompany` 异常，则单条提醒文案为 `请帮忙为俞新硕充值：陪练服务时长不足（剩余0.0，需求1小时）`。
- 若学员本周排了 3 节 30 分钟课、`30分钟剩余 = 2`，则不进入“异常学生”。
- 若学员本周排了 3 节 60 分钟课、`60分钟剩余 = 2`，则不进入“异常学生”。

### 补充验收标准（AC）

1. AC-14：当学员 `30分钟剩余 = 2` 且本周排了 3 节 30 分钟课时，不进入“异常学生”。
2. AC-15：当学员 `60分钟剩余 = 2` 且本周排了 3 节 60 分钟课时，不进入“异常学生”。
3. AC-16：当仅陪练服务时长异常时，单条提醒文案只保留 `陪练服务时长不足（剩余0.0，需求1小时）` 这一异常说明。
4. AC-17：异常学生列表的每一行状态栏都展示 `复制` 按钮，点击后只复制该行对应的单条提醒文案。
5. AC-18：正常学生列表不展示该 `复制` 按钮。

## 13.4 异常学生课时不足订阅补充（2026-08-11）

### 背景

当前 LXLL 未排课课程已支持点击 `订阅`，由后端定时复查并邮件提醒“是否已排课 / 是否已完成”。

但顶部“异常学生”列表仍只有 `复制` 能力。老师在完成充值、补课时调整后，仍需反复手动回到 `schedule.html` 查看该学员的 `30分钟剩余 / 60分钟剩余 / 陪练服务时长剩余` 是否已经恢复，缺少持续跟进抓手。

### 目标

1. 对“异常学生”列表中的李校来啦学员提供与“未排课订阅”一致的 `订阅 / 取消订阅` 能力。
2. 订阅后，系统按小时自动复查该学员的课时余额是否已恢复到“不再属于异常学生”的状态，并发送邮件通知。
3. 一旦检测到本次订阅关注的异常字段已恢复，自动停止订阅。
4. 若连续多次复查后对应字段仍不足，则沿用现有最大提醒次数与自动停订策略，避免无限发信。

### 行为要求

1. 页面范围仍为 `schedule.html` 顶部“异常学生”置顶列表。
2. 仅当该异常学生所属平台为李校来啦时，状态栏展示 `订阅` 按钮；非李校平台不展示。
3. 已订阅后，按钮切换为 `取消订阅`，交互和 loading 文案与未排课订阅保持一致。
4. 点击 `订阅` 后，订阅目标是“当前异常原因是否消失”，不是该学员是否排上课。
5. 订阅检查命中条件：
  - 若订阅时记录的 `zeroFields` 对应额度均已恢复：发送“课时已恢复”邮件并自动停订。
  - 若仍有任一订阅关注字段不足：继续下一轮巡检并发送提醒。
  - 订阅只检查订阅发起时关注的异常字段，不因为其他无关字段恢复或新增而改变当前订阅结果。
6. 同一学员若在异常列表中存在多条异常说明，前端仍按“学员维度”展示一个订阅状态，不按异常类型拆成多条独立订阅。
7. 邮件文案需带上学员名、异常说明摘要、订阅发起日期窗口，以及本轮检测结果（仍不足 / 已恢复）。

### 补充验收标准（AC）

1. AC-19：李校来啦的异常学生行展示 `订阅` 按钮，非李校平台异常学生行不展示。
2. AC-20：点击异常学生行的 `订阅` 后，页面进入已订阅状态，并写入后端订阅存储。
3. AC-21：后台按小时复查该学员在订阅时关注的额度字段是否仍不足；若仍不足则继续按现有策略发提醒。
4. AC-22：一旦检测到订阅关注的额度字段均已恢复，后台发送结果邮件并自动停止订阅。
5. AC-23：异常学生订阅达到最大提醒次数后自动停止继续轮询，不再无限发送提醒。
